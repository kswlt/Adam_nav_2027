## 目前最可信的根因排序

1. **坐标/观测参考混淆**：当前 `sensor_reference` 使用 LiDAR 测量中心 `p_L = p_I + R_I t_{I,L}`，没有云台轴到 LiDAR 的实测机械变换，也没有把底盘中心、云台轴、LiDAR 中心分开发布。若雷达并非与 yaw 轴真正同轴，云台旋转时雷达自然会走圆；若同轴，35cm 量级则更像 LIO 估计误差或安装/时间问题。
2. **云台旋转与 LIO 运动混合**：当前 LIO 只知道 IMU/LiDAR运动，不知道这是云台运动。它可以正确估计传感器轨迹，却不能自动给出底盘轨迹。将 LiDAR odom 直接当底盘导航参考，会把云台扫描造成的变化送入规划/回环。
3. **角度和点云不能严格同步**：电控 RX 记录是主机读到的批次时间，MCU 没有采样时间；当前串口结果不能用于精确的 TF 插值或旋转补偿。
4. **通信抖动曾真实出现**：第二段 RX 有 599 CRC 错误、第三段 33 次。必须保留原始字节，不能简单丢帧后把结果当作连续角度。
5. **供电/初始化条件影响**：此前多次断电和云台未停稳初始化；small_point_lio 会使用初始 IMU 估计重力方向。旋转初始段不能作为静止标定。

## 已定位的设计问题

- `contact_angle` 不能继续只当可视化字段，也不能未经语义验证直接成为 `base_link` 的 yaw。
- 但它也不能替代 LIO yaw；两者来源不同：LIO yaw 是传感器在 odom 中的姿态，`contact_angle` 是电控 RX 的未知机械/差角字段。
- 当前固定场地方向速度转换 `R(-yaw_lio)` 的数学是正确的，前提是 LIO yaw稳定、指令时间与姿态时间匹配，且电控接收的 xy 确实是雷达/yaw水平轴约定。云台旋转时发送固定雷达 +x 只能让车沿当前雷达方向走，不能保持世界固定方向。
- 不能用一个静态 `map→odom`、fake chassis yaw 或把点云轨迹强行投影到地面来掩盖问题。

## 修复顺序

1. 先把串口 RX 记录扩展为每帧单独的主机 system/monotonic 时间（本轮已记录），并为 CRC 错误输出连续坏字节区间；不把未知角度接入 TF。
2. 明确测量 G→L 的水平前后左右偏移；用户此前给出的 G 相对底盘中心左16cm是 C→G，不是 G→L。
3. 做受控数据配对：底盘/云台静止初始化；底盘固定、云台转动；云台固定、底盘走直线；最后叠加闭环。每段写入操作事件标记，确保角度和 MCAP 可对齐。
4. 只有在 G→L 和角度单位/零点/正负已验证后，增加 `gimbal_yaw` 与 `lidar`、`chassis` 的唯一 TF authority；不要向已有 LiDAR TF 旁边再发布冲突父节点。
5. 导航控制继续使用雷达场地参考速度作为临时模式，但要把底盘参考点与雷达参考点的偏心补偿列为未验证；真实轮速/停车反馈接入前不宣称控制闭环完成。
6. 对第三组做离线回环/地图分析，但不把 91 帧或 2.67m 轨迹自动发布成正式地图；正式地图仍需要场地自由空间审核和可复现实车定位。

## 本轮结论

数据备份完成，原始证据没有丢失。现阶段最大问题不是“速度太低”，而是**云台旋转下传感器运动、底盘参考、角度语义和时间同步没有闭合**。软件应先增加明确的轴心/偏心模型和事件对齐，再决定是否让 `contact_angle` 进入 TF；在此之前继续直接依赖雷达 odom 驱动正式导航会把扫描运动当成车体运动。
