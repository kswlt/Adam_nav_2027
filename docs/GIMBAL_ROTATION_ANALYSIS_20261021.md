# 雷达随云台旋转时的位置、方向与初始化分析

分析时供电再次中断，暂停实机操作。本报告基于已下载JSON、实际串口抓包摘要、用户现场描述及本地源码。完整MCAP和逐帧commission poses尚在ASUS，当前未取得完整轨迹做圆拟合，不将下述候选根因当作已证实结论。

## 1. 必须区分两个安装偏移

用户之前确认的安装关系是：底盘中心 C → 左侧16cm的云台轴 G → 同轴LiDAR中心 L。只有底盘旋转时，C→G这个偏移会绕底盘中心旋转；**底盘固定、只有云台转动时，它是一个固定位置，不能拿雷达yaw去旋转这个16cm偏移。**

另一种不同安装是：云台轴 G → LiDAR中心 L 水平偏心16cm。只有这种偏心才会在纯云台旋转时产生最大约32cm的真实圆周位置变化。它与现有约35cm变化量级接近，但当前没有完整轨迹和实测安装证据，不能据此擅自修改外参。

MID-360内部 IMU I→LiDAR L 的配置平移为(-0.011,-0.02329,0.04412)m，水平长度约2.576cm。如果L正好位于固定的云台轴上，I可以绕它转，但仅由这段内部偏移产生的水平任意两点距离不超过约5.151cm；换算到L中心后应该不动。单凭这段内部外参不能解释35cm背景变化。

本地源码 `sensor_reference.py` 调用 `sensor_pose(p_I,q_I,imu_to_lidar)`，实际得到的是：

```
p_L = p_I + R_I * t_I_L
```

它没有云台轴→LiDAR的机械安装变换。因此当前名称“sensor-axis”依赖同轴假设，实际计算点始终是LiDAR中心；不能宣称已恢复真实云台轴或底盘中心。

若纯yaw且L与G同轴、LIO正确，现有换算应保持p_L固定；若L偏心，LIO正常跟踪时p_L本来就应绕圈。不能把真实传感器运动强行归零，也不能只增加一个静态TF来隐藏它。

## 2. 刚才动力测试的方向会随云台改变

`tools/commission_sensor_xy.py` 直接给原 `SerialNode.cmd_vel_callback` 提交恒定雷达系(x=speed,y=0)。它是独立的原协议动力测试，未经过Nav2或生产 `sensor_reference` 的场地系转换。

例如云台转到场地左方，+雷达x就变成向场地左方。同样的报文连续1秒不保证是一条场地直线。刚才的实车移动/停车证明动力响应，不能据此验收规划跟踪。

生产 `sensor_reference.py` 已有 `sensor_velocity(vx,vy,LIO_yaw)`，执行R(-yaw)，设计上可以保持场地速度方向。不能再把编码器角重复旋转一遍；`contact_angle`也不能替换LIO在odom中的yaw。

仍有实际风险：该节点在50Hz tick里用最近一次LIO yaw，现场LIO约10Hz，且当前允许源年龄250ms。这个阈值用于时效健康，不等于高速旋转下的方向精度合格。需要明确姿态与速度指令的时间关系，测量旋转时的方向误差预算，不能简单把姿态写成“最新”就认为已同步。

若以80°/s举例（不是本轮实测转速），10ms时间错位对应0.8°，10m远点的横向误差约14cm；一帧100ms内可转约8°。原始点云因此必须用逐点时间和IMU去畸变，不能只旋转整帧。

## 3. 旋转时初始化是优先排查项

所用small_point_lio的初始化代码，在 `fix_gravity_direction=true` 时收集至少200条IMU，用加速度均值确定初始重力方向。前几次状态重启时云台正在自旋，未完成“底盘和云台都停止”的受控初始化。这是实验缺口，不能把那几轮初始化当作静止验收。

水平旋转且IMU偏离转轴时有向心加速度。仍以80°/s示例：2.576cm半径对应约0.050m/s²，若当成重力约偏0.29°；16cm对应约0.312m/s²、约1.82°。真实结果取决于半径、转速、机械振动和初始化运动，不能用这组示例直接解释6m高度异常。

前一段含抬车的IMU峰值模长约6.93g，属于需进一步核对的强动态样本；模长不等于单轴饱和标志。当前应保留失败样本，检查实际匹配残差、有效对应点、重力/姿态演变和原始数据时序，不放宽漂移门限制造通过。

## 4. 输入断流与旋转误差是不同问题

已实际捕获 `cloud age_s=0.324692` 超过0.25s，且guard锁止；不是“速度太小导致不动”。供电中断本身也会造成真实断流，但此前每次延迟是否由供电造成，没有电压/断电同步证据。

本项目独立Livox进程启用Fast DDS异步发布后，一轮30s空闲+30s录包初始化后未再次锁止，录包阶段guarded cloud最大age约0.105s。它只是短期缓解证据，不能宣称已排除电源问题、长期网络问题或旋转LIO误差。最早observer同步启动bag会阻塞自己1秒，已明确记录这个测量偏差，不将其subscriber gap当成驱动停流证明。

当前健康检查验证消息时效、有限/合法位姿、相邻运动范围及原始点云几何。它没有证明LiDAR长期匹配正确，也没有实测底盘轮速/停车反馈。故不能把healthy=true视为整车导航通过。

## 5. 供电稳定后的采集与判别

先记录原始点云、IMU、LIO IMU位姿、去畸变点云、LiDAR参考位置、TF、输入/状态健康及原因。串口只读保存CRC-valid角度及主机接收时间，明确它不是下位机采样时间，不把未知语义的角度冒充已标定机械yaw。所有阶段保存有时间标记的操作说明。

1. 底盘和云台都停20s，完成初始化并得到静止基线；大流量录制节点尽量在初始化前准备好。
2. 底盘固定，慢转云台；停10s；再反方向慢转。先不叠加车辆平移或抬车。
3. 底盘仍固定，正常扫描速度转动，比较正反方向和不同转速。
4. 云台固定，尺量地面1m往返，单独记录；然后再测扫描时场地固定方向的短程移动。

对纯转动段，用完整p_L和yaw拟合 `p_L = centre + Rz(yaw)*lever_arm`，并检查拟合残差、不同速度/方向的一致性。稳定重复的圆更支持实际偏心；随转速/方向出现滞后更应检查同步；非周期漂移、地图倾斜和去畸变云撕裂应检查LIO匹配。三者可以同时存在，不能单凭图像选择一个。

实测C→G与G→L，确认16cm到底在哪一段。未确认前保留当前配置为待复核，不把假设改成verified。若确有偏心，再计算真实轴心位置及控制参考点；需要的编码器必须先核对含义/单位/正负号/零点/时间，而非直接把115这样的数塞进TF。
